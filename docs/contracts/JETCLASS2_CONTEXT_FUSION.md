# CONTEXT_V1 Oscar fusion contracts

Authority: [active plan](../plans/JETCLASS2_CONTEXT_FUSION_PLAN.md).

New namespace `JC2_CONTEXT_FUSION_*/v1`: SOURCE, PARENT, SPEC, PLAN, PREFLIGHT,
TASK and RESULTS. All carry canonical content hashes, explicit parent hashes
and `final_test_accessed=false`. Original scientific schemas remain unchanged.
Source locks cover tracked reusable package code, thin CLI, environment helpers,
tests and authority documents; old parent source remains pinned separately.

PARENT binds original campaign bytes, exact nine training receipts, U000 reducer,
foundation identity and saved comparison rows. Reuse authenticates payload
bytes and scientific/teacher/population lineage; existence alone is insufficient.
SPEC binds PARENT, SOURCE and canonical graph/recipe/resource registration.
PairedCache refuses differing identities, labels, roles or foundations. Its
transport view axis is routing only, never a model feature or ancestry channel.

PREFLIGHT is bound to exact SPEC/source, site, full counts, installed environment,
single/native-mask/storage parity, actual CUDA offload counters, repeated worst
batch stress, selected-weight/probability readback, measured RSS/GPU/cache bounds
and deterministic maximum-budget runtime projections. Old gate evidence cannot
admit these models. Every science worker validates it before work.

TASK binds SPEC/PREFLIGHT, dependencies' receipts, source/foundation and all
output bytes. Selected training reports retain KERNEL_TRAINING_REPORT and exact
registered recipe/node. Train-only T=2 probability banks retain the original
ordered-identity/class/teacher checks. No validation bank supervises a student.
New reducers publish only train banks; training reports already hold selected
validation metrics. Results label historical versus new fits.

Publication is atomic and non-overwriting. Failed partial directories require
explicit recovery; no implicit restart or destructive cleanup. A completed
receipt is returned idempotently only after reauthentication. Exact-plan
submission rejects stale hashes, wrong authorization and duplicate/ambiguous
claims. No broad job controls, dataset writes or sealed-test capability.
